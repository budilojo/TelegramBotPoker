# UX-Test CardGame

Реализация в `mechanics-overhaul`, ветка `redesign`. Сервер и Telegram этой работой не перенастраивались.

## Что установлено аудитом

- Backend — Node ≥22.5, ESM, grammY long polling, HTTP и WebSocket; frontend — модули без сборки. `server/` и `public/` — отдельный старый продукт, UX-Test их не запускает.
- Подлинность `initData` проверяет `bot/webapp-auth.js`. UX API использует эту же проверку с токеном отдельного бота. ID из JSON не определяет личность или цель сброса.
- SQLite `bot/store.js`: `profiles` — ник/аватар; `train_*` — результаты, уровни, повторение; `decision_log` — решения; `ratings*`/`rating_log` — статистика; `collection_*`, `shop_*`, `pay_*` — оформление и права; `users` — доступность лички/настройка рассылок; `seen` — посещения. Поддержка хранится в `support_*` этой же базы.
- Комнаты целиком сохраняются в `rooms`, группы и запомненное членство — в `groups`; в памяти работают часы, страницы, ограничения частоты и кэш профиля. Действия и собственные представления игроков остаются существующими.
- Браузер: `school.done`, `learn.read`, `learn.quiz`, `train.placed`, `colors.handOrder`, `reactions-off`, `fx-off`, `cosmetics-look` в localStorage; `train.link` в sessionStorage. Их обращения теперь проходят через `miniapp/storage.js`. В UX ключи имеют префикс `cardgame:ux:`, в основной версии имена сохранены.
- Общего onboarding, отдельной системы достижений и уровня аккаунта нет. Есть уровни тренировки. Прогресс обучения на телефоне и серверная тренировка различаются; сброс охватывает оба.
- CloudStorage, DeviceStorage, SecureStorage и сторонней персональной аналитики код не использует. Имеющиеся `events`/`product_use` служат агрегатным метрикам. Для добровольной записи с возможностью удаления добавлены две таблицы **в ту же тестовую SQLite**, без внешнего сервиса: `ux_session` и `ux_event`.
- Основные настройки запуска: BOT_TOKEN, DB_PATH, PORT, BIND_HOST, WEBAPP_URL, MINIAPP, ADMINS, ADMIN_BOT_TOKEN, SALES_MODE, TG_TEST_ENV, SHOP_ENABLED, COLLECTIONS_DEMO, SKILL_RATING_SHADOW. Боевой `.env` не читался.

## Изоляция и запуск

`npm run ux` читает **только `.env.ux` и UX-переменные**, не загружает основной `.env`. База фиксирована: `data-ux/ux.db`; `DB_PATH` основной среды игнорируется. Символические ссылки на каталог/базу и жёсткие ссылки на базу запрещены. Существующая база принимается только с меткой `s:ux-environment = "ux-test"`, проверяемой в read-only режиме **до** открытия Store. Платежи и витрина выключены, админский бот и теневой рейтинг не наследуются. Рабочие игровые модули используются без копий.

Для запрета доступа к production на уровне ОС подготовлен контейнер: образ не содержит `.env` и production-базу, исходники только для чтения, пользователь `node`, отдельный именованный том, без привилегий и без монтирования production. **Это рекомендуемый способ исследования.** Обычный локальный Node использует отдельный путь и все проверки, но сохраняет права пользователя ОС; для строгой файловой изоляции нужен контейнер либо отдельный системный пользователь.

1. В этой папке: `cp .env.ux.example .env.ux`. Файл игнорируется Git. Заполнить локально; токен в чат не отправлять.
2. Указать UX_BOT_TOKEN, UX_BOT_ID нового бота и UX_PRODUCTION_BOT_ID основного (только числовой ID, не токен). Совпадение ID блокирует запуск. Указать отдельный HTTPS UX_WEBAPP_URL, короткое имя UX_MINIAPP, UX_TESTERS — ID тестировщиков через запятую без пробелов. Респондентам допуск в этот список для обычной игры и согласия на запись не нужен.
3. Локально: Node 24, `npm ci`, `npm run ux`. Слушает 127.0.0.1:8081. Нужен HTTPS-туннель на этот порт, **с отдельным адресом**, совпадающим с UX_WEBAPP_URL.
4. Для контейнера после отдельного решения о запуске: `docker compose -f deploy/ux.compose.yaml up --build -d`. Перед этим задать HTTPS reverse proxy отдельного домена на 127.0.0.1:8081. Пример блока Caddy:

```caddy
ux.example.org {
  reverse_proxy 127.0.0.1:8081
}
```

Существующий production-блок не заменять. Боевые тома/базы и токены не передавать контейнеру. Здесь контейнер **не запускался**: Docker daemon недоступен; конфигурация подготовлена, сборка требует отдельной проверки. Выкатка не выполнялась.

## Подключение тестового бота

1. В официальном @BotFather выполнить `/newbot`, создать отдельного бота с отличимым названием CardGame UX-Test и username. Новый Telegram-аккаунт не нужен.
2. Сохранить выданный токен только локально в UX_BOT_TOKEN. UX_BOT_ID — число перед двоеточием. UX_PRODUCTION_BOT_ID — числовой ID основного бота; его токен не переносить.
3. `/newapp`: выбрать **нового** бота, заполнить предлагаемые BotFather название, описание, изображения, URL тестовой HTTPS-среды и short name (например `cardgameux`). Short name записать в UX_MINIAPP.
4. При желании: `/mybots` → новый бот → Bot Settings → Configure Mini App; настроить главное приложение на тот же тестовый адрес. Меню приложения можно настроить через `/setmenubutton`. Названия экранов BotFather могут различаться между клиентами.
5. Добавить нового бота **в отдельную тестовую группу**, сохранить privacy mode. Написать `/game`, открыть приложение из его кнопки. Проверить пометку UX-Test. Не добавлять тестового бота в рабочие группы исследования.

Команды и принципы Mini Apps сверены с [официальной документацией Telegram](https://core.telegram.org/bots/webapps) и [BotFather](https://core.telegram.org/bots/features#botfather).

## Сброс и первый запуск

Кнопка UX-Test находится отдельной строкой над приложением. Панель доступна после серверной проверки Telegram; управляющие кнопки — только ID из UX_TESTERS.

- **Сбросить тестовый профиль**: подтверждение, серверная проверка прав, транзакция удаления только собственных строк, очистка собственного кэша и ключей UX, перезапуск на начальном экране. Telegram ID, имя/фото Telegram и состояние самого Telegram сохраняются. После сброса может понадобиться снова нажать Start у бота или `/game` в тестовой группе: сервер больше не помнит знакомство.
- **Первый запуск**: начальный экран существующего приложения, прогресс не удаляется; общего onboarding для показа нет. Сервер принимает этот маршрут исключительно в UX для тестировщика; подписанная личность неизменна.
- **Очистить локальные данные**: удаляются только ключи `cardgame:ux:` в обоих хранилищах, серверный профиль сохраняется; интерфейс перезапускается.
- Если вы участник незавершённой игры или хост лобби, сброс отвечает 409 с объяснением. Сначала выйти/закончить игру штатно. Автоматически завершать игру за остальных панель не будет. Отказ ничего не стирает; повторить сброс после выхода.

Сохраняются общие справочники, игровые настройки, группы (удаляется только собственное запомненное членство), агрегатные события, архивы совместных партий, `party_day`, общий аудит рейтингов/админских операций. Их удаление затронуло бы других. Поэтому это свежий **личный профиль**, а не очистка всей истории тестовой среды.

Для последовательных респондентов на одном устройстве используйте отдельные браузерные профили/Telegram webview либо заранее выполните очистку UX-ключей. UX-префикс отделяет версии, но не несколько Telegram-аккаунтов, использующих одно браузерное хранилище.

## Исследование и результаты

Респондент открывает тестового бота своим обычным Telegram-аккаунтом. До начала задания открывает UX-Test → читает пояснение → «Согласен, начать запись» → закрывает окно. Запись по умолчанию выключена, после перезагрузки автоматически не возобновляется. «Остановить запись» блокирует дальнейшее добавление на сервере; «Удалить запись этой сессии» удаляет события и её идентификатор. Полный сброс удаляет все собственные исследовательские сессии. После остановки запись остаётся для анализа до удаления.

Каждое событие: случайный UUID сессии с сервера, серверное время в миллисекундах Unix, имя события, экран, известный game ID при наличии. Переписка, карты, URL, текст ошибок, initData и токены в события не принимаются. Владение сессией проверяется на сервере. Техническая таблица связывает UUID с Telegram ID только для прав и удаления; экспорт исследователя ID не содержит.

События: app_open (начало записи после согласия), home_view, game_select, room_form_open, room_settings_change, room_created (только после состояния комнаты с сервера), invite_open (реальное окно приглашения турнира), game_start, error, scenario_exit (скрытие webview). Закрытие/аварийное завершение webview может оборвать последнюю отправку. События описывают интерфейс, не являются игровым аудитом или доказательством успешного приглашения.

Исследователь: UX-Test → **Скачать события**. JSON содержит первые 10.000 событий, упорядоченные по времени; по session можно восстановить шаги и задержки. Лимиты: 2.000 событий на сессию, 20 сессий на пользователя, 180 запросов в минуту. Перед новой сессией удаляйте прежнюю, если она больше не нужна; сохраняйте экспорт до удаления. Для больших исследований можно прочитать всю `ux_event` из **копии тестовой базы** штатным SQLite; production для анализа не открывать.

Для задания «от первого запуска до комнаты» дайте респонденту кнопку из `/game` тестовой группы. Он сам выбирает игру, открывает форму, меняет параметры и создаёт лобби; друзья присоединяются по карточке бота в группе.

**Существующие ограничения сценария:** у обычного группового лобби нет выбора количества мест и отдельной кнопки приглашения внутри Mini App. Число участников определяется игрой; приглашение — карточка в Telegram-группе, её открытие вне приложения мы не наблюдаем. Изменение количества соперников доступно в игре с ботами, количество мест и явная ссылка приглашения — в покерном турнире. Для полного сценария с этими двумя контролами используйте существующий турнир; для обычного карточного лобби отметьте эти шаги как отсутствующие. Они не имитируются и новая игровая функциональность здесь не добавлялась.

Заглушка этого не доказывает. Новая среда с настоящими реквизитами пока не поднята.
