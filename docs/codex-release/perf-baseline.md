# Исходные локальные измерения I для L — 31.10.2026

До первой правки приложения, исходный `8ab9c33`, macOS 25.6.0 arm64, 10 логических
ядер, Node 24.12.0, Chromium Playwright. Только временная SQLite, localhost,
подписанные тестовые личности и TelegramStub; ни секретов, ни сервера.

Команда: `node --expose-gc --disable-warning=ExperimentalWarning tools/perf-baseline.mjs`.
Сырые сводные значения — `perf-baseline.json`. Три повтора одним процессом;
каждый с новой SQLite и браузером/контекстом, файлы ОС уже могут быть в кэше.
Нагрузка: 10 играющих шахматных столов, 20 WS, по 20 refresh с интервалом 250 мс
(400 на повтор), 10 реальных e2-e4 через WS, 10 reconnect, 100 сохранений SQLite;
первая видимая доска на 320×568. Таймауты и ошибки бросают исключение, после
закрытия всех страниц проверяется sessions=0. Завершены все три повтора.

**Ограничения:** одновременно стартовал исходный полный e2e. Это честно
зафиксированная исходная точка до правок, не изолированный бенчмарк. p95 при
n=10 равен максимуму, поэтому в таблице назван максимумом; по трём открытиям
нельзя оценить надёжный p95. Event loop около 11 мс включает разрешение таймера,
не означает зависания на 11 мс. Node CPU/RSS не включают процессы Chromium.
Первая доска не включает запуск Chromium и загрузку настоящего Telegram SDK.
GC и ссылки инструмента влияют на heap; это не доказательство утечки или её
отсутствия. Нет ботов/долгого прогона, мобильной сети и webview.

L: прогнать этот же инструмент без параллельных проверок до своих правок и после;
добавить нагрузку с ботами, длительность, перерисовки/long tasks и несколько игр.
Не выводить из этих чисел ёмкость продакшена. Первая короткая проверка
`load-check.mjs` описана в `baseline.md`; её 0 таймеров/подписок после cleanup —
отдельный факт, не замена длительному наблюдению.
