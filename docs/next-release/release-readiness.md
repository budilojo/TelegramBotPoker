## 3. Что E проверил сам и что исправил

**Известное падение** `bot/battleship.bot.test.js` («expected bot1, actual 101»). Воспроизведено (подменой `Math.random`,
один раз из ~460 запусков; при постоянном «случае» бота 0.34 — каждый раз). Причина — **в тесте, не в продукте**: тест
ждал начала боя шагами по 1 с; бот запирал флот и через 700–1500 мс стрелял внутри того же шага; при промахе ход по
правилам переходил к человеку, и проверка «сейчас ход бота» падала. Доказательство: в момент падения `match.first` = бот,
`log[0].by` = бот, `r: "miss"`. Исправление: ожидание шагом 100 мс (бот физически не успевает выстрелить) и отдельная
проверка `match.first`. Продукт не менялся. «На зубы»: поломка «во второй партии первым стреляет хост» — тест упал.

**Уязвимость зависимостей.** `npm audit`: high — `body-parser < 1.20.9` (DoS сжатым телом запроса), moderate — `qs ≤ 6.16.0`.
Достижимость: `express` подключён **только** в старом Chip Table (`server/index.js`), там нет `express.json`/`urlencoded`,
т. е. парсер тела не вызывается; Mini App (`bot/`) `express` не использует, сервис запускает `bot/index.js`
(`deploy/worldcard.service`). Практически недостижима. Исправлено совместимым `npm audit fix` (без `--force`): меняется
только `package-lock.json` (`body-parser` 1.20.9, `qs` 6.16.2, `express` остаётся 4.22.3); после — 0 уязвимостей,
`npm test` и e2e зелёные.

**Платежи (матрица B).** Прочитан код `bot/payments/` и `bot/app.js` (маршрутизация), повторены `bot/payments.test.js`
(41 сценарий: успех, отмена, двойные нажатия и события, подмены цены/покупателя/валюты/вещи со страницы, чужой счёт,
устаревший счёт, пересечения комплекта, обрыв связи, падение посреди выдачи, перезапуск, сверка, возвраты и их таймауты,
права владельца, остановка продаж, обслуживание, журнал без имён, чужая история) и `node tools/payments-teeth.mjs` —
35 из 35 поломок ловятся. Подтверждено чтением: выдача только по `successful_payment` в одной транзакции; pre_checkout во
время обслуживания и после `/salesstop` отклоняется, пришедшая оплата выдаётся; `TG_TEST_ENV=1` переключает бота в
тестовую среду Telegram (`environment: 'test'`), так что тестовая цена на рабочем боте невозможна; цены — только с
сервера, демо-цены каталога видны лишь в демо-режиме.

**Нет покупки преимуществ.** Продаётся только «Графит» (рубашка, стол, знак, комплект); правила игр не читают ни
коллекции, ни платежи (в `bot/games/` — только рамка и «снимок оформления» в виде дурака); «рейтинг не тянет косметику» —
тест D; «Ночной казино-клуб» в продаваемое не попадает — тест и «на зубы».

**Документы против поведения — найдено и исправлено:**
- карточка вещи, состав покупки и описание счёта обещали «**Навсегда**», а проект условий (п. 3.3) — «пока приложение
  работает» (п. 8.2 — предупреждение о прекращении). Заменено на «Пока работает приложение»; окончательную формулировку
  подтверждает юрист. Защищено тестами (счёт, карточка в двух e2e), «на зубы»;
- правила возврата и инструкция поддержки называли несуществующую кнопку «Поддержка по покупкам» — исправлено на
  «Мои покупки и поддержка» → «Написать в поддержку»;
- `/paysupport` не ссылался на правила возврата и не предупреждал о мошенниках — добавлено (тест, «на зубы»).

**Мелкое, найденное глазами на снимках:** у дуэлей в каталоге и в сообщении `/game` было «2–2 игроков» — теперь «2 игрока»
(тест группы и проверка в `e2e-catalog`, обе «на зубы»).

**Откат на старый код.** B этого не запускал. E запустил: база с оплаченной покупкой (новый код) → старый код сервера
`3a7fcc8` (в отдельной папке `/tmp`) открыл её, схема 5, создал стол, проглотил `successful_payment` без падения, таблицы
`pay_*` не тронул → новый код снова видит покупку.

**Восстановление из копии** (как `deploy/backup.sh`: `sqlite3 .backup` → gzip → распаковка): копия снята до второй
покупки; после восстановления `PRAGMA integrity_check` = ok, схема 5, сверка с Telegram (заглушка) вернула покупку ровно
один раз, повторная сверка ничего не удвоила. Тонкость: распакованная копия в режиме WAL без файла `-shm` **не
открывается** через `sqlite3 -readonly` («unable to open database file») — смотреть копию нужно на её копии без
`-readonly`; а при восстановлении на сервере удалять старые `bot.db-wal` и `bot.db-shm` до запуска.

## 4. Что не проверено и что красное

- **Живой Telegram и телефон — ничего** (у E нет доступа). Всё из §6 — на владельце.
- **Тестовая среда Telegram для оплаты** — не проверена (П-9).

  постоянным — снимки нажимали «Вернуться к столу · Дурак» вместо карточки игры; исправлено в `tools/preview.mjs`.
  Причину плавающих таймаутов не нашёл — записано в задачи.
- Формы настроек остальных игр (кроме покера и дурака) отдельно браузером не проверялись (так и у C).
- Сервер не осматривался: площадка, шифрование диска, журналы.
- `pravo.gov.ru` у A не открылся — законы сверены по вторичным источникам.

## 5. Единый список для владельца (окончательный)

2. **Реквизиты продавца:** ФИО ИП, ИНН, ОГРНИП, адрес для обращений. *Блокирует продажи.*

   *Блокирует продажи.*
4. **Товар и цены:** продаём ли текущий арт «Графита» (да / ждать другой); цены в Stars для рубашки, стола, знака и
   комплекта; комплект при частично купленном — не продавать (как сейчас) / продавать «дополнение» по цене ___.

5. **Юрист:** вычитка `legal/` и 8 вопросов `legal-readiness.md` §13, плюс: подходит ли формулировка «Пока работает

   *Блокирует продажи.*
6. **Сервер и данные:** в какой стране и у какого провайдера сервер и бэкапы; подано ли уведомление в Роскомнадзор;

10. **Рейтинг:** ответить «да / нет / другое» на 8 вопросов `rating-review.md` §6. *Блокирует только открытие рейтинга.*

## 6. Телефонный чек-лист (iPhone и Android, по возможности оба)

Desktop, маленький экран 320 px вживую, планшет.

**а) Бесплатное (после выкатки):**

## 7. Проект плана выкатки (НЕ выполнялся)

Только с отдельного разрешения владельца, по `docs/next-deploy-prompt.md` (там обязательный `/pause`). Что поменять в
этой инструкции перед выкаткой (сейчас она устарела: «около 1000 тестов», «новых зависимостей нет»):

1. **До выкатки:** на выкатываемом коммите `npm test`, `npm run e2e`, `layout`, `kit`, `contrast`. На сервере проверить,
   что в `.env` нет `SALES_MODE=live` (`grep -c '^SALES_MODE=live' .env` → `0`; значение не печатать).
2. `/pause` (админ-бот). Во время обслуживания новые счета и pre_checkout отклоняются, уже пришедшие оплаты выдаются
   (тест «обслуживание: …»). Пока продажи закрыты, оплат быть не может вовсе.
3. Ветки — fast-forward, без `--force`; `deploy/update.sh` (бэкап → тесты на копии → `npm ci` — подтянет новый lock с
   `body-parser` 1.20.9 → перезапуск).
4. Проверки «живое» из инструкции + новое: бот подписан на `pre_checkout_query` (в журнале нет ошибок `allowed_updates`);
   `/sales` у владельца — причина «Режим продаж выключен (SALES_MODE не задан)»; `/paysupport` у игрока — «Продажи ещё не открыты»;
   новые таблицы `pay_*` в `.tables` (`sqlite3 -readonly`, схема 5).
5. Телефон — §6а. Потом `/resume`.
6. **Откат:** если продажи не открывались — как обычно (код назад, база не трогается: проверено E, старый `3a7fcc8`
   открывает базу с `pay_*`). Если продажи когда-то будут открыты — сначала `/salesstop`, дождаться в `/sales`
   «в пути: 0», `deploy/backup.sh`, затем откат; после возврата новой версии сверка подберёт пропущенные оплаты
   (`payment-design.md` §11). При восстановлении базы из копии — остановить сервис, удалить `bot.db-wal` и `bot.db-shm`.
7. Открытие продаж — **отдельный** шаг, после §5 п. 1–8: заполнить `offers.json`, `PAY_SUPPORT`, документы «Действует»,
   `SALES_MODE=live`, перезапуск, `/sales` — «открыто».
