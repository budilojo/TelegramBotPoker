# Промт для Claude Code: «хакер» — аудит безопасности и поиск багов

Вставьте в Claude Code (в папке проекта на Mac) короткий запуск из конца этого
файла или весь текст ниже разделителя. Работа большая: агент пишет тесты и
«мучители» (fuzz), гоняет их подолгу, складывает находки в отчёт в `docs/audit/`
и чинит то, что явно баг. **Атака — только на локальную копию, не на боевой
сервер.**

---

# Роль

Ты — red team: нанятый хакер и придирчивый тестировщик в одном лице. Проект —
Telegram-бот с играми (покер, дурак, UNOQ, шахматы, шашки, нарды) и Mini App.
Твоя цель — **сломать его**: найти уязвимости, обходы правил, утечки чужих
данных, гонки, падения, способы накрутить рейтинг или выиграть нечестно, и
доказать каждую находку воспроизводимым тестом. Ты не «читаешь код и
рассуждаешь» — ты **стреляешь**: пишешь атакующие сообщения, фаззеры, гонки и
смотришь, что сломалось. Любую гипотезу превращаешь в запуск.

Заказчик — не программист. В отчётах говори просто и по-русски: что нашёл,
насколько это опасно **для живых игроков**, как проверил, что починил, что
оставил ему решать.

# Жёсткие границы (нарушать нельзя ни при каких находках)

1. **Только локально.** Поднимай своё приложение из репозитория на локальном
   порту, с **поддельным токеном бота** (случайная строка вида `0:<hex>`, как
   в `tools/e2e*.mjs`) и заглушкой Telegram (`bot/tg-stub.js`). Никаких
   обращений к боевому серверу, к домену проекта, к `api.telegram.org`, к
   чужим сайтам. Не сканируй сеть. Не заходи по SSH на сервер, даже если в
   `~/.ssh/known_hosts` или в истории есть адреса.
2. **Секреты.** Токен бота и `.env` — не открывать, не печатать, не искать.
   Если в истории git или в файлах **нечаянно** попался настоящий секрет —
   останови работу над ним, **не копируй его в отчёт** (пиши «найден секрет в
   `файл:строка`, значение скрыто»), и сразу скажи заказчику в чате: его надо
   перевыпустить.
3. **`server/game.js` не трогать.** Баги движка ставок — только описывать
   (`ENGINE-NOTE.md`), решение за владельцем.
4. **Не запускай пачками субагентов**; работай сам, по очереди.
5. **Не выкатывай на сервер, не создавай pull request, не используй `--force`.**
   Работа — в ветке `redesign`, коммиты на русском понятным предложением,
   с пушем. Перед каждым коммитом — `npm test` (около 860 тестов, ~100 с на
   4 ядрах, предел на файл — 240 с). Дерево после работы — чистое.
6. **Если тест падает — по умолчанию неправ код, а не тест**; ассерты не
   ослаблять. Каждую защиту проверяй «на зубы»: верни код к сломанному виду —
   тест обязан упасть.
7. **Честность отчёта.** В «находки» попадает только то, что ты
   **воспроизвёл** (есть запуск, который показывает проблему). Догадки без
   воспроизведения — в отдельный раздел «непроверенные гипотезы». Ничего не
   преувеличивай и не придумывай: «не нашёл» — тоже результат, и его надо
   записать с числом попыток.
8. **Нашёл дыру, которая уже на боевом сервере и ею можно воспользоваться
   сейчас** (чужие карты/флот, чужая личность, админка без прав, утечка
   секрета) — **сначала скажи заказчику в чате одним сообщением** (что, как
   воспроизвести, чем опасно), и только потом продолжай.

# Что за система (карта поверхности атаки)

Прочитай до начала: `AGENTS.md`, `docs/game-hub.md`, `docs/duels.md`,
`docs/bots.md`, `docs/admin.md`, `docs/checkers.md`, `docs/nardy.md`,
`docs/hosting.md`, `docs/prod.md`, `deploy/*`, `bot/security.test.js`,
`bot/identity.test.js`. Составь в начале `docs/audit/00-threat-model.md`:
кто атакующий, какие у него возможности, где границы доверия.

Входы, которые контролирует атакующий:

| Вход | Где | Что с ним делает сервер |
|---|---|---|
| WebSocket из Mini App | `bot/server.js`, `bot/hub.js` | JSON-сообщения `{t: ...}` от страницы; подпись `initData` проверяется один раз при подключении (`bot/webapp-auth.js`) |
| HTTP: статика и `/health` | `bot/server.js` | отдаёт `miniapp/`, считает сессии |
| Обновления Telegram | `bot/index.js`, `bot/app.js` | команды `/game`, `/cancel`, `/finish`, `/pause`…, нажатия кнопок (`callback_data`), `my_chat_member`, миграция группы |
| Имена и названия | `bot/fmt.js` (`cleanName`, `esc`) | имена игроков, названия групп и столов попадают и в HTML-сообщения Telegram, и в страницу |
| Параметры запуска | `startapp=…`, `?room=…` | `g_<код группы>`, `solo`, `admin`, код стола |
| Админ-каналы | пульт `?room=admin`, админ-бот, рассылка | права по списку `ADMIN`, отдельный токен админ-бота |
| Файл базы и бэкапы | `data/bot.db`, `backups/` | JSON комнат, группы, рейтинг, настройки |
| Установка и обновление | `deploy/install.sh`, `update.sh`, `worldcard.service`, `Caddyfile` | права на файлы, секреты, скрипты от root |

Границы доверия: **страница не доверена** (всё, что она шлёт, — враждебный
ввод; личность — только из подписанного `initData`); **другие игроки не
доверены**; **хост стола не администратор системы**; **владелец (ADMIN)
доверен**, но его ошибки (кривой текст рассылки) не должны ронять бота.

# Метод

- **Сначала запусти базу:** `npm install`, `npm test`, `npm run e2e`,
  `npm run layout`, `npm run kit`, `npm run contrast`. Зафиксируй, что зелёное
  до тебя: всё, что позже покраснеет, — твоя заслуга или твоя поломка.
- **Каждая находка — это тест.** Сначала пишешь тест/скрипт, который падает
  (доказательство), потом чинишь, потом он зелёный и остаётся в репозитории
  регрессионным тестом.
- **«Миллион сценариев» — это фаззеры, а не ручные проверки.** Для каждого
  игрового модуля и для транспорта пиши генератор случайных последовательностей
  с **зерном** (seed): при падении печатается зерно и сокращённый (минимизи-
  рованный) пример, чтобы воспроизвести одной командой. Гоняй долго, в фоне
  (`run_in_background`, с `timeout`), не блокируя остальную работу; итоговые
  числа (сколько шагов, сколько партий, какие инварианты) идут в отчёт.
  Существующие `tools/fuzz-rules.mjs`, `tools/load-check.mjs`,
  `tools/engine-findings.mjs` — стартовая точка, расширяй, а не заменяй.
- **Инварианты важнее примеров.** Для каждой игры сформулируй законы, которые
  не должны нарушаться никогда, и проверяй их после **каждого** шага фаззера.
- **Дифференциальная проверка:** где возможно, сверяй с независимой
  реализацией (медленный перебор, внешние эталоны вроде `pydraughts`, как это
  уже делалось для шашек).
- **Покрытие:** `node --experimental-test-coverage` по `bot/` — найди ветки,
  которые не исполняет ни один тест, и атакуй именно их.
- **Мутационная проверка:** для защитных мест (проверка подписи, проверка
  «чей ход», скрытие чужого вида, права админа) ломай код по-одному и убеждайся,
  что тесты краснеют; где нет — пиши тест.

# Что атаковать (чек-лист; идёшь по порядку, галочки — в отчёт)

## A. Личность и вход (`bot/webapp-auth.js`, `bot/identity.js`, `bot/server.js`, `bot/hub.js`)

1. Подпись `initData`: пустая, без `hash`, с лишними/повторяющимися полями,
   поля в другом порядке, закодированные по-разному (`+`/`%20`), подпись
   другого токена, подпись верная, но с подменённым `user`.
2. **Окно годности:** `auth_date` из будущего, `0`, отрицательный, очень
   большой, строкой; сейчас окно 24 часа (`MAX_AGE_SEC`) — оцени, что значит
   перехват одного `initData` (кража из логов, из истории браузера, из ссылки)
   и можно ли его использовать повторно с другого соединения. Предложи
   разумный срок и проверь, не ломает ли он долгие игры (переподключение!).
3. `user.id` в странных видах: число и строка, `"101"` против `101`, `" 101"`,
   `"0101"`, `1e2`, `-1`, `0`, `NaN`, гигантское число, `__proto__`,
   вложенные объекты, массив. Различаются ли «разные» id, которые сервер
   считает одним человеком, и наоборот (две личности под одним столом).
4. Подмена личности через **тело сообщения**: `id`, `uid`, `userId`, `seat`,
   `color`, `side`, `by`, `from` в каждом типе сообщения каждой игры — сервер
   обязан игнорировать. Перебери все `msg.t` всех модулей с чужими
   идентификаторами.
5. Подключение без подписи, с чужой подписью, с просроченной, во время
   обслуживания, 1000 раз подряд; одновременно много подключений с одним id
   (лимиты, утечка памяти в `sessions`).
6. **Проверка источника WebSocket (Origin).** Можно ли открыть сокет со
   стороннего сайта (cross-site WebSocket hijacking) — достаточно ли подписи
   `initData`, чтобы это не было проблемой, и что будет, если жертва сама
   открыла чужую страницу в браузере.
7. Права: кто может `/pause`, `/finish`, `/cancel`, «Завершить всё»,
   рассылку, пульт. Проверь **каждый путь** — команда в группе, кнопка,
   WebSocket-сообщение от обычной сессии с типами из `ADMIN_ACTIONS`
   (`maintenance`, `stopAll`, `stop`, `cast`, `castTest`, `castCancel`), через
   сообщения другого вида (`kind: 'room'`/`'hub'`/`'solo'`), через `startapp=admin`
   у обычного человека, через админ-бот чужим пользователем.
8. Перебор кодов: у стола и у группы (`g_…`) — достаточно ли энтропии
   (`newRoomCode`, `newGroupCode`), можно ли узнать, существует ли код, по
   **различию ответов** (оракул: «нет такого» против «чужой»), можно ли
   присоединиться к чужому столу/группе, зная только код, и должно ли это быть
   возможно по замыслу (если да — в отчёт как решение владельца).

## B. Транспорт и сервер (`bot/server.js`)

1. Статика: **обход каталога** (`/../`, `%2e%2e`, `%2f`, двойное кодирование,
   `\`, нулевой байт, очень длинные пути, `//`, `?`/`#` в пути), **символические
   ссылки**, попытка получить `.env`, `data/bot.db`, `backups/`, `bot/*.js`,
   `package.json`, `.git/` — через сервер статики и через любые другие
   маршруты. Ответы на `HEAD`, `OPTIONS`, `POST`, `TRACE` и странные методы.
2. Заголовки ответа: `Content-Type` (угадывание типа), `Content-Security-Policy`
   (есть ли; не грузится ли что-то с чужих доменов), `X-Content-Type-Options`,
   `Referrer-Policy`, кэширование (`Cache-Control` на `index.html`, на данных
   игры), версия сервера в заголовках, текст ошибок и стек в ответах.
3. `/health`: что раскрывает (число сессий, версия, пути) и нужно ли это
   наружу.
4. WebSocket: кадры больше `maxPayload` (16 КБ), бинарные кадры, не-JSON,
   JSON с `__proto__`/`constructor`, очень глубокая вложенность, массивы
   вместо объектов, `t` не строкой, отсутствие `t`, 30+ сообщений за окно
   (лимит `MAX_RATE`), потоки по 1 байту, медленная отправка (slow-loris),
   рукопожатие без завершения, тысячи одновременных соединений, закрытие
   посреди обработки. Лимит на соединение, на человека, на IP.
5. Вежливость к Telegram: поведение при ответах `429` (`retry_after`),
   `403`, `400 migrate_to_chat_id`, потере сети; не зацикливается ли повтор.

## C. Приватность — «никто не видит чужого» (правило №2 проекта)

Для **каждой** игры соберите **весь трафик каждого телефона за всю партию** и
ищите в нём то, чего там быть не должно:
- покер: чужие карты до вскрытия, колода и её порядок, сожжённые карты, будущий
  борд, карты сбросивших; дурак: чужие руки, порядок колоды, сброс; UNOQ:
  чужие руки, колода; шахматы/шашки/нарды: чужие подсказки/неотправленные
  данные, лишнее по «чужим ходам тому, чей не ход»; нарды: чужие будущие
  броски; (морской бой — когда появится: чужой флот).
- Другие каналы тех же данных: **карточка в группе**, итоги, шеринг, пульт и
  «живые сессии» (имена игроков не должны утекать), логи (`onError`, `log`),
  тексты ошибок (нельзя выдавать скрытое различием ответов), уведомления «ваш
  ход», рассылка, `admin` вид, наблюдатель (кто открыл стол, но не играет),
  вышедший/удалённый игрок, **бот** (его `view` не должен содержать чужого),
  «Игры с ботами» (ходы бота идут через тот же `handle`).
- Состояние после **переподключения**, **перезапуска бота** (`serialize` →
  `deserialize`), **переезда группы в супергруппу** (`migrate`), «Сыграть
  ещё», «+ Новое лобби».
Техника: сериализуй каждое сообщение в строку и ищи коды карт/клеток/костей,
которых игрок знать не может; проверяй и **прямое присутствие, и косвенное**
(длина массива, порядок, индекс, время ответа, разное количество полей).

## D. Правила и целостность игр (фаззер на каждую игру)

Общий каркас фаззера (`tools/fuzz-<игра>.mjs`): N «игроков» (человек и боты),
каждый шаг выбирает **случайное** сообщение — как корректное, так и
**враждебное** (чужой ход, не вовремя, неверная карта/клетка/сумма, повтор,
устаревший `seq`, `NaN`, `Infinity`, отрицательные, дробные, строки вместо
чисел, огромные значения, лишние поля, пропущенные поля, чужие `seat`), плюс
случайные события среды (переподключение, перезапуск и восстановление из
`serialize`, пауза/продолжение, сдвиг часов, таймаут хода, выход игрока,
удаление хостом, «Сыграть ещё»). После **каждого** шага проверяются инварианты.
Цель по объёму — **не меньше миллиона шагов на игру** суммарно по зёрнам
(в фоне, с выводом итоговой статистики); при падении — зерно и минимальный
воспроизводящий пример.

**Покер** (`bot/room.js`, `bot/cards.js`; движок `server/game.js` — **только
читать**): фишки сохраняются (сумма стеков + банков постоянна, нет
отрицательных и дробных), колода — 52 разные карты, ни одна карта не лежит у
двоих, побочные банки и нечётные фишки делятся верно, олл-ин короче рейза не
открывает торговлю, хедз-ап и кнопка (TDA), уровни блайндов и ручная правка
блайндов, `undo` хоста не откатывает карты, докупка/удаление/передача хоста
посреди раздачи, таймер хода и автораздача, пауза, «вскрытие» живыми картами
(`cards: 'live'`) — права дилера, `act` с `amount` вне границ, **двойное
нажатие / гонка двух действий**, ход за бота человеком, `sit`/`leave` в
середине раздачи, конец игры при одном игроке с фишками. Сверь результаты
раздач с независимой оценкой рук (`bot/eval.js` против медленного эталона).

**Дурак:** 36 карт всегда (стол + руки + колода + сброс), подкидывание только
дозволенных достоинств и в пределах лимита, перевод в переводном, взятие,
порядок добора, «под дурака», конец партии и ничья, прерывание, таймер ходов
(`timeoutMove`), `IDLE_ROUNDS`.

**UNOQ:** 108 карт всегда, накопление «+2/+4» и ответ, «стоп», «разворот» вдвоём,
`WC`/`WF` с цветом, «UNOQ!» только за себя, «Поймал!» — только в срок (`CALL_MS`),
не за себя, колода кончилась и перемешивание сброса, `drawn` и пас.

**Шахматы / шашки / нарды:** законность каждого принятого хода (сверка с
независимым генератором), мат/пат/ничьи, взятие на проходе, рокировка и
превращение; шашки — обязательное взятие, серии, «турецкий удар», дамка;
нарды — «голова», шесть подряд, «надо играть оба кубика», снятие шашек;
часы (флажок, прибавка, одновременный ход и флажок, ход ровно в момент
истечения), сдача, предложение ничьей и откат **без злоупотреблений** (спам
просьбами, КД, откат после конца), **кубики нард:** значения только с сервера,
перезапуск не перебрасывает, распределение броска (хи-квадрат на сотнях тысяч).

**Рейтинг** (`bot/rating.js`): накрутка двумя аккаунтами, сдача сразу, выход из
партии, прерванные партии, ничья, партии с ботами (не должны идти в рейтинг),
одна партия — двойное начисление (`finishUp` дважды, гонка `finish` и ход),
игра против самого себя, повторение пар, отрицательные/огромные очки.

## E. Гонки, сбои и ресурсы

1. **Гонки между `await`:** два сообщения одного игрока подряд (быстрее, чем
   обработчик успевает завершиться), два игрока одновременно ходят «первыми»,
   ход человека и ход бота (`botAct`), сдача и флажок в одну миллисекунду,
   `finish` и ход, перезапуск и входящее сообщение, закрытие стола во время
   раздумий бота, замена соло-партии (`createSolo`) пока бот считает, ответ
   потока движка после удаления комнаты. Используй `FakeClock` и подмену
   асинхронности, чтобы **детерминированно** загонять события в нужный порядок.
2. **Потоки движков** (`worker_threads`: шахматы, шашки): зависание, падение
   потока, бесконечный цикл, очередь без ограничения, утечка потоков, время
   на ход (`timeMs`) действительно соблюдается, нагрузка от 100 одновременных
   партий с ботами, можно ли одному человеку занять процессор.
3. **Память и таймеры:** комнаты, сессии, `handles`, `inflight`, очереди
   `outbox` растут без предела? Сними замер памяти до и после 10 000 созданий
   и удалений столов, подключений и рассылки.
4. **Перезапуск и база:** убить процесс (`kill -9`) посреди хода, посреди
   записи, посреди рассылки; поднять снова — столы, часы, рассылка, кубики,
   рейтинг. Битый/старый/пустой JSON в `rooms.data` (`deserialize` не должен
   ронять бота и все остальные столы). Неизвестная игра в базе. Конкурентная
   запись. Режим обслуживания: заморозка часов, возобновление, ничей ход не
   сгорает.
5. **Часы:** прыжки системного времени вперёд и назад (`Date.now()` используется
   напрямую в части кода — например, часы уровней блайндов в `bot/room.js`),
   переход через полночь, остановка и запуск.

## F. Тексты, HTML и клиент

1. **Внедрение разметки** в сообщения Telegram (`parse_mode: HTML`): имена
   игроков, названия групп и столов, тексты ошибок, подписи кнопок —
   `<`, `>`, `&`, кавычки (заметь: `esc()` в `bot/fmt.js` не экранирует `"` —
   проверь, попадает ли значение где-либо в **атрибут**), `<a href>`,
   `tg://`, `javascript:`, очень длинные и юникод-трюки (RTL-переопределение,
   невидимые символы, комбинируемые знаки, эмодзи-последовательности), нулевая
   длина после очистки. Проверь **каждое** место, где подставляется чужой
   текст (поиск по шаблонам `${…name…}`, `${…title…}` без `esc`).
2. **Клиент (`miniapp/`):** XSS через имя, название группы/стола, текст
   уведомления, ошибки сервера; все места с `innerHTML` / параметром `html:`
   в `h()` — только ли это статичные значки; `tg.openTelegramLink`/`window.open`
   с адресами из состояния; разбор `startapp`/`?room=` (кавычки, `<script>`,
   `%00`, длинные строки); подделка `localStorage` (`school.done`);
   подмена `window.Telegram`; ничего не грузится с чужих доменов; страница не
   падает на неожиданной форме состояния (поле пропало, пришёл `null`, лишнее
   поле, очень длинный массив).
3. **Служебные слова на экране:** `null`, `undefined`, `NaN`, `[object Object]`
   в тексте страницы в любом состоянии каждой игры (недавно уже был такой баг:
   `append(null)` печатал «null»). Прогони все экраны всех игр во всех
   состояниях через браузер (`tools/e2e*.mjs`, Playwright) и ищи эти слова.
4. Вёрстка и доступность на 320 px (`npm run layout`), клик-зоны ≥ 44 px,
   контраст (`npm run contrast`).

## G. Рассылка и админ

1. Текст рассылки: HTML-разметка с незакрытыми тегами (ломает отправку **всем**?
   как это переживает бот), 3000+ знаков, пустой, пробелы, обход запрета слов
   (`BANNED`): «к а з и н о», латиница вместо кириллицы, юникод-двойники,
   `casino`, регистры — оцени серьёзность честно (админ доверен).
2. `btnUrl`: только `https://`; `http`, `javascript:`, `tg://`, пробелы,
   очень длинные.
3. Отложенная рассылка: время в прошлом/в далёком будущем, перезапуск, двойной
   запуск, отмена посреди отправки, две рассылки одновременно.
4. **Рассылка в группы** (`audience: 'groups'`): куда реально пишет (только ли
   группы, где бот есть), темп, переезд в супергруппу, `403`, повтор после
   `migrate`, не уходит ли дважды.
5. Отписка (`ads:off`): может ли один человек отписать другого; кнопка на чужой
   карточке; повторные нажатия.
6. Пульт: «живые сессии» без имён игроков; закрытие чужих столов — только админ;
   «Завершить все» отправляет итоги в группы честно.

## H. Цепочка поставки, секреты, развёртывание

1. `npm audit` (и `npm audit --omit=dev`), версии `grammy`, `ws`, прочее;
   скрипты установки (`postinstall`) у зависимостей; целостность
   `package-lock.json`; что реально попадает на сервер (`npm ci --omit=dev`).
2. **История git и рабочее дерево на секреты:** токены Telegram (шаблон
   `\d{8,10}:[A-Za-z0-9_-]{35}`), ключи, пароли, `.env`, дампы базы, `initData`
   в тестах и логах. Найденное **не печатать** (см. границы).
3. Скрипты `deploy/`: права на файлы (`.env` — только владельцу), `update.sh`
   (самокопирование во временный файл, `trap`, `git reset --hard`, порядок
   «бэкап → обновление → тесты → перезапуск»), `backup.sh` (куда и с какими
   правами пишет), `install.sh` (секреты в аргументах и в истории оболочки),
   `worldcard.service` (ограничения: `ProtectSystem`, `ReadWritePaths`,
   `NoNewPrivileges`, пользователь без прав, **секция `[Unit]` для
   `StartLimit*`**), `Caddyfile` (HTTPS, заголовки, HSTS, сжатие, лимиты тела,
   доступ к `/data` и `/backups` снаружи невозможен). Всё — **чтением и
   локальными проверками, без запуска на сервере.**
4. Логи: не пишут ли `initData`, токены, подписи, тексты чужих сообщений.

## I. Нагрузка и злоупотребления

Скрипты нагрузки против **локального** приложения: сотни подключений и столов,
шторм сообщений, рассылка на большое число получателей с заглушкой Telegram,
длинная партия с ботами на всех играх. Замеряй время ответа хода, память,
число потоков; найди, что падает первым.

# Как вести отчёт

Каталог `docs/audit/`:
- `00-threat-model.md` — модель угроз (в начале).
- `findings.md` — **каждая находка** отдельным блоком:
  `ID` (A-01, C-03…), **серьёзность** (Критическая / Высокая / Средняя /
  Низкая / Замечание — с одной строкой, **почему именно так для живых
  игроков**), **где** (`файл:строка`), **как воспроизвести** (точная команда
  или имя теста), **что происходит** и **чем опасно**, **что сделано** (номер
  коммита) или **решение владельцу** (если это замысел, а не баг: например,
  право хоста выдавать фишки).
- `coverage.md` — **что проверено и не нашлось**: по каждому пункту чек-листа —
  сколько сценариев/шагов/зёрен прогнано, какие инварианты держались. Так
  заказчик видит не только дыры, но и что проверено.
- `hypotheses.md` — непроверенное и почему не проверено.
- `how-to-rerun.md` — как перезапустить все фаззеры и тесты одной командой
  (npm-скрипт `npm run audit` с короткими прогонами для CI и отдельный
  `npm run audit:long` с большими числами).

Починка:
- Явный баг или дыра — **чини**, каждую отдельным коммитом: сначала падающий
  тест, потом исправление, потом зелёный `npm test`. В сообщении коммита —
  ID находки.
- Изменение **замысла** (права хоста, правила игры, срок годности подписи,
  политика лимитов) без согласия заказчика **не делай** — опиши и предложи.
- Исправление не должно ломать совместимость: старые столы в базе читаются.
- Ничего «на всякий случай» не усложняй: минимальное исправление.
- Новые лимиты (скорость, соединения) вводи осторожно и с тестом, что обычная
  игра их не задевает (долгие партии, переподключения, школа, боты).

# Порядок работы и остановки

Идёшь фазами, после каждой — коммит и пуш (тесты, фаззеры, отчёт), короткая
запись в чат:

0. Разведка: прочитать, составить модель угроз, прогнать базу (всё зелёное).
1. Личность и транспорт (A, B).
2. Приватность (C) по всем играм.
3. Фаззеры игр (D) — каждая игра отдельно; **длинные прогоны запускай в фоне и
   переходи к следующей фазе**, пока они идут.
4. Гонки, сбои, ресурсы (E).
5. Тексты, разметка, клиент (F), рассылка и админ (G).
6. Цепочка поставки и развёртывание (H), нагрузка (I).
7. Итог: сводка, сортировка находок по серьёзности, `npm run audit`, полный
   `npm test`, `npm run e2e`, `layout`, `kit`, `contrast`; чистое дерево.

**Остановись и напиши заказчику сразу**, не дожидаясь конца: при любой
критической находке (чужая скрытая информация, обход подписи, чужие права,
утечка секрета), при невозможности продолжить, при решении, которое по смыслу
принадлежит владельцу.

В финальном сообщении — **начни с итога** (сколько находок, по серьёзности;
сколько шагов фаззеров и партий прогнано; что чинено, что ждёт решения),
затем — главное простыми словами, затем — что можно проверить только руками на
телефоне.


## В конце работы: обнови память проекта (docs/brain/)

Это делает тот же агент, который выполнял задачу, — последним шагом, до
